# AGENTS.md — POS Project

This file is read by AI coding agents (Claude, Codex, or any other assistant) working in this repository. Follow it every session.

## Protocol — read this first, every session
1. Before doing anything else, read `AGENT_MEMORY.md` in this same directory. It is the running handoff log of what previous sessions — by any agent, on any branch — have done, decided, and left unfinished.
2. Do the work the user asked for.
3. Before ending your turn / handing off, append a new dated entry to `AGENT_MEMORY.md` (format is documented inside that file). Do this whether or not the user explicitly asks — this is how the next agent (or your own next session) picks up context without the user having to re-explain "here's what changed so far".
4. Keep entries factual and specific: what changed, which files/modules, why, what's left open. Skip filler and skip restating things that are already obvious from git history.
5. Never overwrite past entries — only add new ones, newest at the top.

## Project overview
POS is a multi-module point-of-sale system:
- `back-end/` — Java Spring Boot API, built with Maven (`mvnw`). Runs against Postgres via `docker-compose.yml`.
- `web/` — TypeScript monorepo using pnpm workspaces + Turborepo (`apps/`, `packages/`, `tooling/`).
- `mobile_desktop/` — Kotlin Multiplatform app via Gradle (`androidApp/`, `desktopApp/`, `shared/`).
- `doc/ERD` — entity-relationship diagrams for the data model.

## Branching
- `main` — stable/release branch.
- `develop` — integration branch.
- Feature work happens on scoped branches (`feature/*`, `backend/*`, `mobile/*`, etc.) merged via PR.
- Check `git branch --show-current` for the branch actually checked out right now — it changes between sessions.

### One command for a fresh clone (`start.sh`, since 2026-11-13)
- `./start.sh` (repo root; Linux and macOS, Windows through WSL) starts the backend with Postgres and Mailpit in Docker, builds the desktop app while the backend boots, waits for the backend and opens the app. Closing the app stops the containers (the data stays). `./start.sh backend | app | stop | logs | reset | help` do one part each.
- Docker side: root `docker-compose.yml` (project `pos`; services `db`, `mail` = Mailpit, `backend` built from `back-end/Dockerfile` as `pos-backend:local`, local profile; volumes `db_data` and `uploads`). It's separate from `back-end/docker-compose.yml` (`pos-db` + `pos-mailhog`, for running the jar yourself): own containers and database, and the database port isn't published. Ports `POS_API_PORT` (8080) and `POS_MAIL_PORT` (8025), bound to `POS_BIND` (127.0.0.1); the backend gets this computer's time zone (`POS_TZ`). `back-end/.dockerignore` is an allowlist (`.mvn`, `mvnw`, `pom.xml`, `src/main`), so `target/`, `uploads/` and `.env*` never go to Docker.
- On this machine your own backend and MailHog hold 8080/8025, so plain `./start.sh` stops at its port check. Try it with `POS_API_PORT=18080 POS_MAIL_PORT=18025`.
- Desktop side: `./gradlew --no-daemon` with the Kotlin compiler in-process, so nothing stays running after the app closes; the app finds the backend through `SAPORINI_API_BASE_URL`; on Linux the screen scale comes from `Xft.dpi` (as `run-desktop.sh`). Java: JAVA_HOME, PATH or macOS `java_home` if it's a JDK (with javac) 17–25, Gradle 9.1's range (raise `JAVA_MAX` in the script when Gradle is updated); otherwise Amazon Corretto 21 (what `gradle-daemon-jvm.properties` asks for, so Gradle doesn't fetch a second JDK) is downloaded from corretto.aws (sha256 checked) into `.tools/` (gitignored). The desktop build needs no Android SDK (checked 2026-11-13: a full compile with no SDK and no build cache works).

### Backend
- Build the runnable jar with `./mvnw -o package -Dmaven.test.skip=true`. `-DskipTests` does NOT skip tests here (the pom wires surefire's `skipTests` to `${skip.unit.tests}`).
- Local backend runs as `java -jar target/pos-0.0.1-SNAPSHOT.jar` from `back-end/` against the podman `pos-db` container (db `pos_local`, user `pos_user`). The local schema is `foundation_local`, and Flyway history is `foundation_local.flyway_schema_history`.
- Stop the running backend before (or right after) rebuilding the jar. A running process whose jar was replaced starts answering 500s.
- Integration tests (`*IntegrationTest`, `*IT`, failsafe) use Testcontainers on podman. Start the socket with `systemctl --user start podman.socket`, then run with `DOCKER_HOST=unix:///run/user/1000/podman/podman.sock TESTCONTAINERS_RYUK_DISABLED=true`.
  - Everything: `./mvnw -o verify` (1,264 unit tests and 331 ITs as of 2026-10-07).
  - Unit tests only: `./mvnw -o test -Dtest=Name`.
  - One IT: `./mvnw -o verify -Dskip.unit.tests=true -Dit.test=Name -Dfailsafe.failIfNoSpecifiedTests=false`.
- API-level ITs extend `integration/support/AbstractPosApiIntegrationTest` (schema `pos_api_it`, `newWorld()`, `staff()`, `token()`, `menu()/item()/order()`, `setting()`). It fails any test that produced a 500, so every bad input must come back as a 4xx.
- Input rules: every `@RequestBody` is `@Valid`, and every free-text field has a `@Size` (2000 for notes/descriptions unless the column says otherwise). Bodies over 1 MB get a 413, and list page sizes are capped (`PageableUtils`). `GlobalExceptionHandler` turns database errors and entity rule failures into 400/409.
- `open-in-view` is off, so anything outside a service transaction that touches a lazy relation fails with LazyInitializationException (a 500). Live-update `subscribe` methods (`OrderChangeNotifier`, `TableLayoutChangeNotifier`) are `@Transactional(readOnly = true)` for their branch check; give new SSE subscribe methods the same.
- Native SQL (`nativeQuery = true`) must write tables as `{h-schema}table`. Hibernate's `default_schema` (`foundation_local` locally) doesn't reach native SQL, so an unprefixed table works in prod (public schema) but fails locally with "relation does not exist".
- Stock movements (`POST …/inventory/receive|waste|transfer|returns|adjustments`), order writes and payments go through `OrderWriteFilter`: movements and payments need an `Idempotency-Key` header (16–100 chars of `[A-Za-z0-9_-]`), otherwise a 400 with an empty message.
- One open order per table (user, 2026-11-01: "a table can not have two orders"), whatever `allow_open_tickets` says (Open tabs only covers orders with no table). Held by the partial unique index `uk_orders_one_open_per_table` (V114, which first cancelled empty extra orders and took the table off extras with dishes) and by `OrderSupport.assertTableCanReceiveOrder` (400 "T05 already has an open order") for creating, moving and splitting onto a table. A split with no table named gets no table. `reopenOrder` drops the table when it has a new order. Joining combines orders (`order/service/TableOrderCombiner`: the start table's order stays; a joined table's order with no dishes is cancelled; other orders' dishes and kitchen tickets move into it by `{h-schema}` native updates, discounts become fixed amounts, the emptied order is CANCELLED with "its dishes moved to …"); unmerging combines any leftovers the same way. `TableOrderCombiner` flushes before the kept order takes the table, so the index never sees two.
